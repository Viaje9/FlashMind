# 四區塊回顧品質標準

依序呈現下列四部分。目的是讓使用者知道「我當時想說什麼、下次能怎麼說」，不能只報告實際用字與推薦清單。展示內容與保存 JSON 必須一致，不另外產生較簡略的保存版。

## 1. 可以說得更自然的地方 → `result.review`

按對話情境組織，完整對話通常挑 3–6 個有價值的表達重點；短對話可更少，不硬找錯誤。每個重點包含：

- 用繁體中文說明使用者當時想表達的意思。
- 引用相關原句或指出卡住的表達。引文須忠於原始文字，不能把修正句冒充原句。
- 給一至兩個自然、完整、適合 B1 的英文說法。
- 解釋為何這樣較貼切，或哪個字可以替換原本難以組織的說法。

欄位內使用 `### 情境標題`、中文短段落與 `> 英文例句`，不要再加入四個主要部分的標題。區分「文法錯誤」與「原句可理解，但能說得更自然」。不把助理問得不清楚、轉錄不確定之處都歸咎於使用者。

保留原意和範圍：白板只用於工作，不等於刻意建立生活界線；某一部舊影集加速播放，不等於所有舊影集都加速。延伸句須標示為可選說法，不得冒充使用者的原有想法，也不可放進忠實摘要。原文太短或不清楚時，誠實說明限制。

例如原文說 `fast mode` 並解釋空閒時間不足，可以建議：

> My free time is limited, so I watch this series at a faster speed.

說明 `limited` 表達時間有限、`at a faster speed` 指加速播放，與跳過內容的 `fast-forward` 不同。只寫「推薦 limited」不算完成回顧。

## 2. 這次實際使用的單字 → `result.actualUses`

只列出使用者在原始對話中真正拿來表達意思、且符合目標字庫與證據規則的單字。不能把助理說過、單純跟讀、詢問字義，或在回顧中才出現的字算進來。

| 單字 `term` | 意思與使用情境 `expressionContext` | 你當時的原句 `evidence[].quote` | 更自然的說法 `naturalSentence` |
| ----------- | ---------------------------------- | ------------------------------- | ------------------------------ |
| task        | 任務：描述完成一項工作             | I finish task.                  | I finish a task.               |

原句直接引用真正的 user 訊息，保留原本用字與錯誤；有多段證據時分段呈現。自然句放在另一欄，不修改原文去製造使用證據。`expressionContext` 同時說明詞義與本次表達情境。

沒有符合證據的實際用字時，保留此區塊並說明「本次沒有可確認的實際使用目標單字」。新草稿缺少引文時不可猜測，須修正草稿或移除沒有證據的項目；顯示既有紀錄缺證據時則明確標示「未提供原句證據」。

牌組候選與狀態放在這張表下方；候選只能來自實際使用的目標字，不代表已建卡，也不能把所有推薦字當成牌組候選。

## 3. 建議練習的單字 → `result.recommendations`

先依真實表達需求挑字，再核對最新目標單字與 canonical ID。優先選前面能實際改善表達的字，不為填滿表格硬推薦。無適合字時保留空陣列，展示「本次沒有需要額外推薦的目標單字」及可先練習前述說法。

每筆資料都必須能組成這個表格：

| 單字 `term` | 意思與使用情境 `expressionContext` | 可練習的句子 `naturalSentence` | 推薦原因 `recommendationReason`                        |
| ----------- | ---------------------------------- | ------------------------------ | ------------------------------------------------------ |
| limited     | 有限的：說明空閒時間不多           | My free time is limited.       | 可替換反覆使用的 not enough time，讓原因更容易說清楚。 |

`expressionContext` 同時包含本次詞義與使用者想表達的意思；`naturalSentence` 是完整 B1 句子且包含目標字；推薦原因要具體，不寫「很實用」「符合對話」就結束。字庫釋義若不合本次情境，說明差異，例如 episode 是「一集」、plot 才是「劇情」，不自行修改字庫。

「實際使用」與「推薦練習」分開。原始逐字稿、修正句、推薦句也必須分開；此表或英文摘要出現的字，不能反過來算成使用者的實際用字。

## 4. 可朗讀的英文摘要 → `result.summary`

寫第一人稱的自然英文短文，使用 B1 句型及短段落，保留重要主題、原因、偏好、計畫和差別。完整對話通常約 120–220 字；短對話不擴寫湊字數，重要內容較多時可適度延長。

自然使用前面幾個實用表達，不硬塞所有推薦字。不得混入中文、標題、條列、教學說明或助理才提出的想法。不加入新的情緒或動機；不確定之處仍保留不確定性。這裡的「可朗讀」是能直接拿來口說練習的短文，不表示已產生音訊。

## 展示前檢查

- 是否真的解釋了「為什麼這樣說」，而不只稱讚或糾正文法？
- 推薦字是否補上本次真正的表達需求，每個都有具體情境、例句和原因？
- 英文短文是否忠實、讀得順，且沒有把延伸建議變成事實？
- 四部分是否完整呈現並與 JSON 一致？實際使用表格的原句是否忠於 user 逐字稿，且與自然句分開？
- 牌組候選放在實際使用表格下方；下次計畫與驗證結果放在四部分後面，不取代主要內容。

CLI 驗證能查結構、ID 與用字證據，不能證明內容有教學價值；以上仍須逐項閱讀確認。
